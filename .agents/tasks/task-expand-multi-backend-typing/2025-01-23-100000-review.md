# Multi-backend injection system with failover chain

This change adds 8 new keystroke injection backends (AutoHotkey, NutJS, UIAutomation, ElectronWebContents, VirtualKeyboard, BatchPaste, HybridTyping, PowerShellAddType) to the existing 4, wires them through a new BackendManager that provides failover with health tracking, updates TypingManager to delegate backend resolution and failover to the manager, and adds a TypingSettingsView with backend selection, failover chain reorder UI, and health display. The BaseBackend interface is expanded with capability-reporting methods and lifecycle aliases (pause/resume/abort/cleanup/typeText).

**Watch for:** Command injection via VirtualKeyboardBackend's `injectKey` method which interpolates `keyCode` directly into a PowerShell script without validation (confirmed). Silent error swallowing across all backends means failover decisions are made without distinguishing transient failures from permanent unavailability (confirmed). The "type caching" claim in PowerShellAddTypeBackend doesn't persist across invocations because each `execFile` spawns a fresh PowerShell process (confirmed). Duplicate backend resolution maps in both TypingManager and BackendManager (confirmed — a maintenance hazard but not a bug).

## High-level view

The BaseBackend interface grows four capability-reporting methods (`supportsRealtimeStreaming`, `supportsKeyCombos`, `supportsUnicode`, `supportsChunking`) and four lifecycle methods (`pause`, `resume`, `abort`, `cleanup`), all with no-op/false defaults. `typeText` is added as an alias for `inject`. This lets the scheduling layer query what a backend can do without instanceof checks, though nothing in BackendManager or TypingManager currently reads these capabilities.

BackendManager owns backend instantiation, the failover chain, and health stats. On injection failure it walks the chain trying each available backend. Health is error-count + last-error-time; there's no circuit-breaker or cooldown, so a flapping backend can be retried indefinitely on every call.

TypingManager uses BackendManager for initialization and failover but maintains its own `_resolveBackendClass` map — an exact copy of the one in BackendManager — as a direct-instantiation fallback. This creates two copies of the name-to-class mapping that must be kept in sync.

The 8 new backends split into three categories: PowerShell-based P/Invoke wrappers (VirtualKeyboard, PowerShellAddType, UIAutomation), external-tool launchers (AutoHotkey), optional-dependency wrappers (NutJS), and composition backends (BatchPaste, HybridTyping, ElectronWebContents). All PowerShell-based backends use Base64 for the text payload but interpolate configuration values (delay, keyCode) directly into scripts.

TypingSettingsView adds a backend dropdown with 12 options, a failover chain reorder list with up/down buttons, and a health grid showing availability and error counts per backend. The UI talks through `window.cheatingDaddy.typing` IPC — no new IPC handlers are visible in this diff so the TypingManager must already be wired up from a previous change.

<summary>Issues (7)</summary>

1. **Command injection in `injectKey`** — `VirtualKeyboardBackend.injectKey` and `PowerShellAddTypeBackend.injectKey` (via `.inject(String.fromCharCode(keyCode))`) interpolate values into PowerShell commands. While `injectKey` receives a number from internal code today, any external caller passing a crafted keyCode could inject arbitrary PowerShell. Validate that `keyCode` is a finite integer before interpolation.
2. **AutoHotkey script injection** — `AutoHotkeyBackend.inject` escapes backslash, double-quote, and backtick in the text payload, but does not escape `{` or `}` which are special in AHK SendText. Additionally, newlines in the input text will break the `SendText "..."` single-line format. Use AHK's file-read pattern or escape newlines.
3. **PowerShellAddType "caching" is per-process** — Each call spawns a new powershell.exe, so `Add-Type` runs every invocation. The `_typeCompiled` flag is tracked in JS but doesn't change the script behavior. For actual caching, keep a long-running PowerShell process or compile to a temporary DLL.
4. **No failure propagation from backends** — Every backend catches errors silently (`catch (e) {}`). BackendManager.tryInject relies on thrown errors to trigger failover. If a backend returns without typing but also without throwing (the current pattern), failover never triggers.
5. **Duplicate `_resolveBackendClass` maps** — BackendManager and TypingManager each have an identical name→class map. Extract a shared mapping module or have TypingManager delegate entirely to BackendManager.
6. **Capability methods unused** — `supportsRealtimeStreaming`, `supportsKeyCombos`, `supportsUnicode`, `supportsChunking` are declared on all backends but never read by BackendManager, TypingManager, or the scheduler. They're dead code until a consumer is added.
7. **VirtualKeyboardBackend truncates scan codes** — `(byte)(scan & 0xFF)` in the C# code passes only the low byte of the Unicode char to `keybd_event`. Characters above U+00FF (most non-Latin scripts) will be garbled despite `supportsUnicode()` returning true.

## Command injection surface in PowerShell backends

VirtualKeyboardBackend.injectKey interpolates `keyCode` directly into a heredoc-style PowerShell script:

```javascript
[VKKeyHelper]::keybd_event(${keyCode}, 0, 0, [UIntPtr]::Zero)
```

If `keyCode` is not sanitized and ever receives a string (e.g., from deserialized JSON), this becomes a PowerShell injection vector. The same pattern appears in Win32SendInputBackend.injectKey (pre-existing, not new in this diff) but is replicated in VirtualKeyboardBackend and indirectly in PowerShellAddTypeBackend via `injectKey → inject(String.fromCharCode(keyCode))`.

More critically, `AutoHotkeyBackend.inject` constructs an AHK script file with user text embedded:

```javascript
SendText "${text.replace(/\\/g, '\\\\').replace(/"/g, '""').replace(/`/g, '``')}"
```

This escapes three characters but AHK's SendText still interprets `{` and `}` as special (raw key names). A text payload containing `{Enter}` would inject a literal Enter key press. Also, newlines in `text` break the single-line `SendText "..."` statement — the script becomes syntactically invalid.

## Silent error swallowing defeats failover

Every backend's `inject` method catches errors and returns void:

```javascript
} catch (e) {
    // VirtualKeyboard injection failed
}
```

BackendManager.tryInject expects a thrown error to trigger the failover walk:

```javascript
try {
    await primaryInstance.inject(text);
    return { success: true, backend: this._primary };
} catch (e) {
    this._recordError(this._primary, e);
```

Since backends swallow their errors, the primary always reports success even when text was not injected (PowerShell timed out, target window lost focus, AHK binary not found after initialization, etc.). Failover never activates. The fix is either to rethrow errors from inject or to return a result object indicating success/failure.

## PowerShellAddType "caching" is illusory

The backend tracks `_typeCompiled` in JS but the script itself already handles the check:

```powershell
if (-not ([System.Management.Automation.PSTypeName]'CachedSendInput').Type) {
    Add-Type ...
}
```

However, each `execFileAsync('powershell', ...)` spawns a fresh process. Types compiled with `Add-Type` live in the process's AppDomain and are gone when the process exits. The conditional check passes every time because it's always a new process. Actual caching requires either a persistent PowerShell process (via stdin/stdout IPC) or pre-compiling a .dll to disk and loading it with `Add-Type -Path`.

## VirtualKeyboard Unicode truncation

The C# interop code casts the Unicode character's scan code to `byte`:

```csharp
keybd_event(0, (byte)(scan & 0xFF), KEYEVENTF_UNICODE, UIntPtr.Zero);
```

`keybd_event`'s `bScan` parameter is a single byte, which means only the low 8 bits of the character are sent. For characters above U+00FF (accented Latin beyond Latin-1, CJK, Cyrillic, etc.), this produces garbage. The `supportsUnicode()` method returns `true`, which is misleading. If this backend intends Unicode support, it should use `SendInput` with `KEYEVENTF_UNICODE` (which takes a full `ushort` scan code in the `KEYBDINPUT` struct) instead of `keybd_event`.

## HybridTypingBackend creates fresh instances on `isAvailable()`

```javascript
isAvailable() {
    const Win32SendInputBackend = require('./Win32SendInputBackend');
    const ClipboardInjectionBackend = require('./ClipboardInjectionBackend');
    const si = new Win32SendInputBackend();
    const cb = new ClipboardInjectionBackend();
    return si.isAvailable() || cb.isAvailable();
}
```

Every call to `isAvailable()` (which BackendManager calls during failover iteration) allocates two backend instances, queries them, and discards them. This is cheap now (just a platform check) but establishes a pattern where availability checks have unbounded cost — especially if a future backend's `isAvailable()` does I/O. BatchPasteBackend has the same pattern.

## BackendManager health has no decay or circuit-breaking

`_recordError` increments `errorCount` and stamps `lastErrorTime` but nothing ever decrements the count or uses it to skip a backend. A backend that failed once an hour ago is indistinguishable from one that failed 500 times in the last second. The failover walk retries every backend in the chain on every call regardless of health. A circuit-breaker (skip backends with N errors in the last M seconds) would prevent repeatedly hammering a consistently broken backend.

## Duplicate name→class mapping

`BackendManager._resolveBackendClass` and `TypingManager._resolveBackendClass` contain identical 30-line maps. If a new backend is added to one but not the other, the system will silently fail to resolve it in one code path. The TypingManager fallback (direct instantiation when BackendManager doesn't have the backend) is only reachable if BackendManager.initialize() was never called or if the backend name isn't in the failover chain. Consider either removing the TypingManager copy or extracting the mapping to a shared module.
