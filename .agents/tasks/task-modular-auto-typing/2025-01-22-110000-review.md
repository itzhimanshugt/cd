# Modular auto-typing engine with keystroke injection backends (v2)

The follow-up commit addresses all seven issues from the v1 review: the backend name map now accepts kebab-case, all `execSync` calls are replaced with async `execFile`, text is Base64-encoded before transmission to PowerShell (eliminating the injection surface), the `fullResponseType` hotkey guards against missing responses, a renderer round-trip auto-loads AI responses into the TypingManager, the HotkeyController has documentation explaining its role, and the clipboard restore timeout is extended to 300ms.

Watch for: `injectKey(keyCode)` in Win32SendInputBackend still interpolates a numeric value directly into the PowerShell script without validation (possible — low risk since `keyCode` is typed as number internally, but there's no runtime guard); the clipboard restore is still timing-based with an arbitrary 300ms constant rather than waiting for paste confirmation (confirmed — acceptable trade-off given platform constraints).

**Verdict**: APPROVED

## High-level view

The async migration is thorough. All three backends and `WindowTargetLock` now return Promises, and the `InjectionScheduler` properly awaits them in its setTimeout loop. The `execFile` function is used with explicit argument arrays rather than shell-string construction, which eliminates the `cmd.exe` intermediate and its metacharacter parsing.

The Base64 encoding approach passes text as UTF-16LE encoded in a single-quoted PowerShell string, where the `[A-Za-z0-9+/=]` alphabet cannot break out of the string context. The `injectKey(keyCode)` method on Win32SendInputBackend still interpolates `${keyCode}` directly — callers pass integers so the practical risk is low, but no runtime guard exists at this boundary.

The auto-load pipeline is now complete: gemini.js emits to the renderer, the renderer calls `typing:auto-load` IPC back to main, and `typingManager.loadResponse()` is called. The round-trip is necessary because gemini.js lacks a direct reference to the TypingManager instance.

## Base64 text encoding closes the injection surface

The fix encodes text as UTF-16LE Base64 and decodes it inside PowerShell:

```js
const base64Text = Buffer.from(text, 'utf16le').toString('base64');
// ...
$bytes = [Convert]::FromBase64String('${base64Text}')
$text = [System.Text.Encoding]::Unicode.GetString($bytes)
```

Since the Base64 alphabet contains no PowerShell metacharacters and is placed inside a single-quoted string (where only `''` is special), arbitrary AI response text cannot escape the string context. The `PowerShellSendKeysBackend` additionally escapes SendKeys special characters (`+^%~(){}[]`) per-character after decoding, wrapping them in braces for `SendWait()`.

The `injectKey(keyCode)` method remains unprotected: `[KeyHelper]::SendKey(${keyCode})`. Callers pass integer virtual key codes, so exploitation would require a bug in a caller passing user-controlled data as a keyCode. A `parseInt` + `isNaN` guard at the method boundary would close this defensively.

## Skip-ahead position reporting

In `skipSentence()`, the scheduler calls `Promise.resolve(this._backend.inject(skippedText)).catch(() => {})` and immediately advances the queue position without waiting for injection to complete. This means progress reporting races ahead of actual keystroke delivery during a skip. For a user-initiated jump this is an acceptable UX trade-off, but it means the "typed" position is not guaranteed to match what has actually been injected into the target window.
