# Modular auto-typing engine with keystroke injection backends

A complete typing injection system that takes AI response text and replays it character-by-character (or chunk-by-chunk) into an arbitrary foreground window, simulating human typing cadence. The architecture splits into a core engine (ResponseBuffer, TypingQueue state machine, HumanizationEngine, InjectionScheduler, AbortController), four pluggable injection backends (Win32 SendInput via P/Invoke, clipboard paste, PowerShell SendKeys, RobotJS stub), orchestration (TypingManager EventEmitter, HotkeyController, WindowTargetLock), and integration wiring across the Electron main process, renderer preload, storage layer, and UI.

Watch for: backend name mismatch between the settings UI and `_resolveBackendClass` map that silently nullifies the injection backend (confirmed); synchronous `execSync` calls in Win32SendInput and WindowTargetLock that block the Electron main thread during typing (confirmed); command injection surface in PowerShell scripts via insufficiently-escaped response text (confirmed); incomplete auto-load flow where AI responses never reach the TypingManager without explicit user action yet the `fullResponseType` hotkey assumes a response is already loaded (confirmed).

## High-level view

The core engine is cleanly layered: immutable ResponseBuffer snapshots feed a TypingQueue state machine, which is driven by an InjectionScheduler that queries a HumanizationEngine for WPM-based inter-keystroke delays. The InjectionScheduler uses recursive setTimeout rather than setInterval, so it naturally self-regulates against backend latency. This design is sound for the character/word/sentence/paragraph granularity modes it supports.

The injection backends all inherit from BaseBackend but share a critical execution model: they spawn synchronous PowerShell processes on every `inject()` call. For the character granularity mode (the default), this means one `execSync` invocation per character typed, each blocking the main process for the duration of process spawn + script execution. At 80 WPM (default) the delay budget per character is ~150ms, and cold PowerShell startup alone can exceed that on many machines.

The integration layer connects the typing system to the rest of the app through IPC handlers, renderer API, hotkey registration, and a settings UI. A naming mismatch between what the UI stores (`'win32-sendinput'`) and what the manager resolves (`'Win32SendInput'`) means the backend silently resolves to `null` when settings are applied, causing all injections to no-op against a stub `{ inject() {} }` fallback.

The response lifecycle has a gap: Gemini responses emit `typing-response-ready` to the renderer, but nothing calls `typingManager.loadResponse()` on the main process side. The user must manually trigger load before typing can start, yet the `fullResponseType` hotkey in window.js calls `start()` without loading, which throws.

<summary>Issues (7)</summary>

1. **Backend name mismatch** — The TypingSettingsView sends `'win32-sendinput'`/`'clipboard'`/`'powershell'`/`'robotjs'` but `_resolveBackendClass()` maps `'Win32SendInput'`/`'ClipboardInjection'`/`'PowerShellSendKeys'`/`'RobotJS'`. Result: backend resolves to null, injections silently no-op. Normalize the map to accept both forms, or change the UI values to match.
2. **Main-thread blocking via execSync** — Win32SendInputBackend, PowerShellSendKeysBackend, WindowTargetLock, and ClipboardInjectionBackend all use synchronous child_process calls. In character-by-character mode this blocks the Electron main thread hundreds of times per response. Switch to `execFile` (async) or batch characters into single script invocations.
3. **Command injection in PowerShell scripts** — Response text is interpolated into PowerShell script strings with only single-quote doubling. Text containing `$()`, backticks, or `"` sequences can escape the string context and execute arbitrary commands. Use Base64-encoded -EncodedCommand or pass text via stdin/pipe instead of string interpolation.
4. **fullResponseType hotkey throws** — In window.js, the `fullResponseType` handler calls `typingManagerRef.start()` without loading a response. If no response was previously loaded, this throws "No response loaded" synchronously inside the hotkey callback. Either auto-load lastResponse (like HotkeyController does) or guard with a check.
5. **No auto-load from AI response** — `typing-response-ready` is emitted to the renderer event bus but no consumer calls `typingManager.loadResponse()`. The typing system can't type responses unless the user manually triggers load. Wire `sendToRenderer('typing-response-ready', ...)` to also call `typingManager.loadResponse(text)` in the main process.
6. **HotkeyController is dead code** — The class is fully implemented but never instantiated in the integration code. Window.js reimplements the same hotkey logic inline. Either remove HotkeyController or use it instead of duplicating logic.
7. **Clipboard restore race** — ClipboardInjectionBackend restores the clipboard after a fixed 100ms `setTimeout`. If the paste hasn't completed (e.g., target app is slow to process Ctrl+V), the user's clipboard is overwritten with the injected text. The restore timing is fragile.

## Backend name mismatch silently disables injection

The settings storage defaults to `backend: 'win32-sendinput'` and the TypingSettingsView dropdown emits values like `'win32-sendinput'`, `'clipboard'`, `'powershell'`, `'robotjs'`. When the user changes the backend via settings, `setupTypingIpcHandlers` in index.js calls `typingManager.setBackend(settings.backend)`, which reaches `_resolveBackendClass`:

```js
_resolveBackendClass(name) {
    const map = {
        Win32SendInput: backends.Win32SendInputBackend,
        ClipboardInjection: backends.ClipboardInjectionBackend,
        PowerShellSendKeys: backends.PowerShellSendKeysBackend,
        RobotJS: backends.RobotJSBackend,
    };
    return map[name] || null;
}
```

None of the settings-format strings (`'win32-sendinput'`) match the map keys (`'Win32SendInput'`). The return is `null`, and `_initBackend` sets `this._backend = null`. In `_createScheduler`, a null backend is replaced with `{ inject() {} }` — a silent no-op. The typing loop runs, positions advance, events fire, but no characters are ever injected.

## Synchronous PowerShell spawning blocks the main thread

`Win32SendInputBackend.inject()` calls `execSync(powershell ...)` for every invocation. In `character` granularity mode (the default), the InjectionScheduler calls `backend.inject(chunk)` once per character. Each `execSync` blocks the Electron main thread until PowerShell finishes. PowerShell cold-start on Windows typically takes 200-800ms; even with `-NoProfile` it's rarely under 100ms. This means:

- At 80 WPM with character granularity, the scheduler expects ~150ms per character but PowerShell takes longer, causing the main process to hang and the app to become unresponsive.
- All IPC, window events, and renderer communication stall during injection.

The same issue applies to `WindowTargetLock.checkFocus()` (though it's not called in the scheduler loop currently) and `ClipboardInjectionBackend._simulatePaste()`.

## Command injection via response text interpolation

The Win32SendInputBackend interpolates response text into a PowerShell script:

```js
const escaped = text.replace(/'/g, "''").replace(/`/g, '``');
// ...
$text = '${escaped}'
```

This escapes single quotes and backticks for PowerShell single-quoted strings, but the script is then wrapped in double quotes for the command line:

```js
execSync(`powershell -NoProfile -NonInteractive -Command "${script.replace(/"/g, '\\"')}"`)
```

The outer `cmd.exe` shell parsing, the double-quote context, and PowerShell's own parsing interact in complex ways. AI response text containing sequences like `$(calc.exe)` or unbalanced quotes could break out of the string context. This is a code execution vector since the response text comes from an AI model whose output isn't sanitized.

PowerShellSendKeysBackend has the same pattern. ClipboardInjectionBackend avoids this by writing to clipboard via Electron's API rather than interpolating text into scripts.

## Incomplete response-to-typing pipeline

The data flow for an AI response is:

```
Gemini turn complete
  -> sendToRenderer('typing-response-ready', { text })
    -> renderer event bus dispatch
      -> (nothing listens)
```

The TypingManager in the main process never receives the response. The only way text reaches it is through the `typing:load-response` IPC handler, which nothing calls automatically. Meanwhile, the `fullResponseType` hotkey calls `typingManagerRef.start()` without checking if a response is loaded:

```js
tryRegister('fullResponseType', keybinds.fullResponseType, () => {
    typingManagerRef.start();  // throws if no buffer loaded
    sendToRenderer('typing-status-changed', typingManagerRef.getStatus());
});
```

The `HotkeyController.registerFullResponse()` method handles this correctly by calling `manager.getLastResponse()` and `manager.loadResponse(lastResponse)` first, but that class is never instantiated in the wiring code.

## Scheduler completion detection with long-running backends

The InjectionScheduler checks `pos >= buffer.length` after scheduling the delay:

```js
const pos = this._queue.getPosition();
if (pos >= buffer.length) {
    this._running = false;
    this.emit('complete');
    return;
}
```

The position is advanced inside the setTimeout callback after `backend.inject(chunk)` returns. With synchronous backends this is fine — the advance happens after injection. But if a backend were made asynchronous (to fix the main-thread blocking), the inject call would return a Promise that isn't awaited, and the position would advance before injection completes. The scheduler loop isn't async-aware, which constrains future fixes.

## WindowTargetLock adds no value without integration

WindowTargetLock implements focus-check via PowerShell GetForegroundWindow, but nothing in the InjectionScheduler or TypingManager calls `checkFocus()`. The module exists as capability without a caller. If integrated, `checkFocus()` uses `execSync` which would add per-character latency to the injection loop.
