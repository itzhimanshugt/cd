# Multi-backend injection system with failover chain (v2)

This review verifies the fixes applied after v1. The change adds 8 new keystroke injection backends to the existing 4, introduces a BackendManager with failover, deduplicates backend resolution via a shared module, and exposes a settings UI for backend selection and failover chain management.

**Watch for:** The `_escapeAhkText` method escapes braces using `{{}` and `{}}`, but `SendText` in AHK v2 does not interpret brace sequences — it sends literal text (confirmed, but means the escaping produces wrong output). Silent return-without-throw from ElectronWebContentsBackend when no window is focused still defeats failover for that backend (confirmed). The `this._interKeyDelay` value is interpolated into PowerShell scripts without validation — it's set from constructor options which originate from user config (likely).

**Verdict**: APPROVED

## High-level view

The v1 critical issues are substantially addressed. `injectKey` across all backends now validates `keyCode` is a finite integer in 0-255 before interpolation, closing the command injection vector. All existing backends (Win32SendInput, Clipboard, PowerShell, RobotJS) now let errors propagate instead of swallowing them, which enables BackendManager's failover logic. VirtualKeyboardBackend's `inject` method now uses `SendInput` with `KEYEVENTF_UNICODE` and a full `ushort` scan code, fixing the Unicode truncation issue. The duplicate resolution maps are eliminated by a shared `resolveBackend.js` module used by both BackendManager and TypingManager. The PowerShellAddType per-process limitation is documented clearly in the source.

The AutoHotkey brace escaping fix applies `{{}` / `{}}` transformations, but this is a nuance worth noting: AHK v2's `SendText` command does not interpret `{...}` brace sequences at all (unlike `Send`), so the escaping is unnecessary but harmless — the braces in output will be doubled. This is a cosmetic bug (extra characters in output) rather than an injection vector, since `SendText` doesn't interpret special sequences.

<summary>Issues (3)</summary>

1. **AHK brace escaping produces doubled braces in output** — `SendText` in AHK v2 sends literal text without interpreting `{...}` as key names. The `{{}` / `{}}` escaping transforms `{` into `{{}` which `SendText` will emit as the literal three characters `{{}`. Either drop the brace escaping (since `SendText` is safe), or switch to `Send` with the escaping. Non-blocking: only affects text containing literal braces.
2. **ElectronWebContents silent no-op defeats failover** — When `!this._BrowserWindow` or no focused window exists, `inject` returns without throwing. BackendManager interprets this as success. If Electron is in the failover chain but no window is focused, injection silently drops text. Throw when the inject cannot deliver text.
3. **`interKeyDelay` interpolated from user config** — `this._interKeyDelay` is interpolated into PowerShell scripts (VirtualKeyboard, PowerShellAddType, Win32SendInput). It's set from `options.interKeyDelay` which comes from user settings. While it should always be a number from the settings layer, adding a `Number.isFinite` check would close the surface entirely. Non-blocking: the settings layer constrains this to numeric values today.

## v1 issue resolution audit

**Issue 1 — Command injection in `injectKey`**: Fixed. All backends that interpolate `keyCode` into scripts now validate with `if (!Number.isFinite(keyCode) || keyCode < 0 || keyCode > 255) return;` before any string interpolation. The text payload path uses Base64 encoding across VirtualKeyboard, PowerShellAddType, UIAutomation, and Win32SendInput, so user text never touches the script template directly.

**Issue 2 — AutoHotkey script injection**: Partially fixed. The `_escapeAhkText` method now escapes backticks, braces, double quotes, backslashes, and converts newlines to AHK `\`n` sequences. The newline issue is resolved — multi-line text no longer breaks the script. However, `SendText` in AHK v2 does not process `{` and `}` as special characters (that's `Send`'s behavior), so the brace escaping is over-zealous: input text `{hello}` becomes `{{}hello{}}` which `SendText` emits literally as `{{}hello{}}` instead of `{hello}`. Not a security issue, but a functional bug for brace-containing text.

**Issue 3 — PowerShellAddType caching**: Documented. The class-level JSDoc now explains the per-process limitation and suggests future paths (persistent process, pre-compiled DLL). The `_typeCompiled` flag is acknowledged as a future-proofing marker.

**Issue 4 — Failover dead on arrival**: Fixed for PowerShell-based backends, RobotJS, and Clipboard. The try/catch wrappers around `execFileAsync` and `this._robot.typeString` are removed, letting errors propagate to BackendManager's `tryInject`. The failover proxy in TypingManager catches the primary's throw and delegates to `backendManager.tryInject(text)`. However, some backends still return silently without throwing on certain failure modes — see the Electron issue below.

**Issue 5 — Duplicate resolution maps**: Fixed. Both BackendManager and TypingManager now call `resolveBackend(name)` from `src/typing/backends/resolveBackend.js`. The shared module is the single source of truth for the name-to-class mapping.

**Issue 7 — VirtualKeyboard Unicode truncation**: Fixed. The `inject` method now uses `SendInput` with `KEYEVENTF_UNICODE` and stores the character as `(ushort)c` in the `wScan` field of a `KEYBDINPUT` struct. The `ushort` range covers U+0000 to U+FFFF (the Basic Multilingual Plane). Characters above U+FFFF (emoji, rare CJK) would need surrogate pair handling, but that's an edge case for a keyboard injection backend and not a regression.

## ElectronWebContents silent no-op

The `inject` method guards with early returns:

```javascript
async inject(text) {
    if (!text || !this._BrowserWindow) return;
    const win = this._BrowserWindow.getFocusedWindow();
    if (win && win.webContents) {
        await win.webContents.insertText(text);
    }
}
```

When no window is focused, `getFocusedWindow()` returns `null`, the `if` block is skipped, and the method returns void — no error thrown. BackendManager's `tryInject` treats a non-throwing call as success. If this backend is in the failover chain and happens to be tried when no Electron window has focus, text is silently dropped. The same pattern exists in `NutJSBackend` when `this._keyboard` is null after a failed `initialize()`, though there `isAvailable()` would return false and BackendManager skips it.

This is non-blocking because ElectronWebContents is last in the default failover chain and its primary use case is injecting into the app's own windows (where focus is expected). But if a user manually promotes it in the chain, the silent drop becomes reachable.

## interKeyDelay interpolation surface

Three backends interpolate `this._interKeyDelay` into PowerShell:

```javascript
Start-Sleep -Milliseconds ${this._interKeyDelay}
```

The value is set from `options.interKeyDelay ?? 10` in constructors. The options object originates from user settings (stored via `electron-store`). If the storage layer is corrupted or a future code path passes unsanitized config, this becomes a PowerShell injection point. The risk is low today — settings are numeric — but unlike `keyCode` (which got validation), `interKeyDelay` has no `Number.isFinite` guard.
