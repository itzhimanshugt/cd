# Phases 2-4: Performance cache, UX polish, and native stubs

This change layers three phases of refactoring on top of Phase 1's store/service/component foundation. Phase 2 introduces an in-memory storage cache with debounced disk flush, wires HotkeyService into window.js for differential shortcut re-registration, removes redundant dual-dispatch events in the renderer, and defers expensive startup work. Phase 3 adds a collapsible hamburger sidebar, migrates AutoTypeView and HotkeysView to shared `cd-*` components, adds a floating status pill overlay, and introduces an AI prompt preview with clipboard copy. Phase 4 drops a NativeHelper stub class and an ARCHITECTURE.md overview.

**Watch for:** The storage cache can lose writes on abrupt process termination since dirty entries are only flushed on a 300ms debounce timer (confirmed). The status pill reads `cheatingDaddyApp._settings.backend` which is undefined on the app element, so it always displays the hardcoded fallback rather than the actual active backend (confirmed). The HotkeyService `updateBinding` skips re-registration when the accelerator is unchanged but also silently discards the new handler, creating a staleness risk if closed-over refs ever change (confirmed).

## High-level view

The storage cache wraps every JSON file read/write behind `_cacheRead`/`_cacheWrite`, and any mutation marks the key dirty for a 300ms debounced flush. This eliminates synchronous I/O on hot paths but introduces a data-loss window: `app.exit(0)` (the emergency quit handler) and normal quit both terminate without calling `flushAll()`.

HotkeyService differential binding compares accelerator strings and skips unchanged bindings. The handlers map is rebuilt from scratch on every invocation of `updateGlobalShortcuts` — each handler is a fresh closure — but the service only compares accelerators, not handler identity. This means if handler logic changes without the accelerator changing, the stale handler stays bound. Currently safe because closed-over refs are stable for the window's lifetime, but fragile.

The status pill overlay in renderer.js attempts to show the active typing backend but reads a property (`_settings`) that belongs to `AutoTypeView`, not `CheatingDaddyApp`. It will always fall through to the hardcoded `'SendInput'` string.

`AICustomizeView._getProfilePrompt()` hardcodes 6 profile system prompts in the renderer. If the main-process copies of these prompts drift, the preview becomes misleading.

The `updatePreference` wrapper fires a toast when `customPrompt` changes during an active session by checking `cheatingDaddyApp.sessionActive`. If `cheatingDaddyApp` is null (DOM not yet connected or during teardown), this throws.

<summary>Issues (5)</summary>

1. **Dirty cache lost on crash/exit** — `flushAll()` is exported but never called from `app.on('before-quit')` or the emergency quit handler. Call `storage.flushAll()` in both paths.
2. **Status pill reads undefined property** — `cheatingDaddyApp._settings.backend` will be `undefined` for the app component, producing "Typing via undefined". Read the active backend from the typing status event's `detail` instead.
3. **Handler staleness after differential skip** — If the accelerator for an action doesn't change but the handler's closed-over refs change (e.g., `typingManagerRef` reassigned), the old closure remains bound. Not currently exploitable since refs are stable, but fragile if lifecycle changes.
4. **Prompt preview hardcodes profile prompts** — `AICustomizeView._getProfilePrompt()` duplicates the profile system prompt strings that presumably also exist on the main process side. If they diverge, the preview is misleading.
5. **Session-active toast null guard** — `cheatingDaddyApp.sessionActive` is read synchronously in the renderer storage wrapper but `cheatingDaddyApp` may be null during startup or teardown. Add a null guard.

## Storage cache flush gap

The cache in `src/storage.js` schedules a 300ms `setTimeout` via `_scheduleDirtyFlush()` whenever a write occurs. The emergency quit handler in `window.js` calls `app.exit(0)` which terminates the process immediately without draining the event loop. The `before-quit` handler in `index.js` calls `stopMacOSAudioCapture()` and `apiKeys.stopBackgroundValidation()` but never `storage.flushAll()`. Any preference change within the last 300ms before a quit is silently dropped.

```javascript
// src/utils/window.js — emergency quit
handlers.emergencyQuit = () => {
    try {
        const { stopMacOSAudioCapture } = require('./gemini');
        stopMacOSAudioCapture();
    } catch (_) {}
    app.exit(0); // <-- flushAll() never called
};
```

Call `storage.flushAll()` before `app.exit(0)` and in the `before-quit` handler.

## HotkeyService handler staleness

The `updateBinding` method compares only the stored accelerator with the incoming one:

```javascript
updateBinding(action, newAccelerator, handler) {
    const entry = this._registry.get(action);
    if (entry && entry.accelerator === newAccelerator) {
        return true; // No change needed — but handler is NOT updated
    }
    ...
}
```

If the accelerator stays the same but the handler changes, the registry keeps the stale handler. The closures capture `mainWindow`, `sendToRenderer`, `geminiSessionRef`, and `typingManagerRef` — all stable for the window's lifetime. This isn't a bug today, but becomes one if window recreation or ref reassignment is introduced later.

## Status pill reads wrong property

```javascript
_eventBus.addEventListener('typing-started', () => {
    const status = cheatingDaddyApp && cheatingDaddyApp._settings
        ? cheatingDaddyApp._settings.backend || 'SendInput'
        : 'SendInput';
    _showStatusPill(`Typing via ${status}`);
});
```

`cheatingDaddyApp` is `<cheating-daddy-app>`. The `_settings` property is defined in `AutoTypeView`, not `CheatingDaddyApp`, so this always hits the fallback. Include the active backend name in the `typing-started` event detail or query `cheatingDaddy.typing.getStatus()`.

## Prompt preview duplication

`AICustomizeView._getProfilePrompt()` hardcodes 6 profile prompts that presumably mirror the main-process session initialization logic. If main-process prompts are updated without updating this renderer copy, the preview shows stale content. Lower risk given it's preview-only, but worth noting for future maintenance.

## Session-active toast null guard

```javascript
// src/utils/renderer.js — inside storage.updatePreference wrapper
if (key === 'customPrompt' && cheatingDaddyApp && cheatingDaddyApp.sessionActive) {
    showToast('Custom instructions updated - will apply on next session');
}
```

The `cheatingDaddyApp` reference is set once at module load via `document.querySelector('cheating-daddy-app')`. If the module loads before the custom element connects (race during startup), this is null and the conditional is safe. However, the assignment happens at module evaluation time — if for any reason the element hasn't been defined yet, `cheatingDaddyApp` is permanently null and the toast never fires. This is a latent failure mode rather than a crash, but worth a defensive re-query.
