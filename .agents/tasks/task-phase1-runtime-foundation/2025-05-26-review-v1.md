# Phase 1 Runtime Foundation: Reactive Stores, Service Layer, and Shared UI Components

This change introduces three new subsystems to the Electron+Lit app: a reactive store layer (renderer-side, ES modules) for shared state, a service layer (main-process, CommonJS) abstracting storage and hotkeys, and a set of reusable Lit web components for settings UI. A proof-of-concept wires `CustomizeView` to use `cd-slider`, `cd-toggle`, and `cd-select` backed by `settingsStore`, and `CheatingDaddyApp` subscribes to `sessionStore` for route-independent session awareness.

**Watch for:** Dual-write pattern in CustomizeView handlers calls both `settingsStore.set()` and `cheatingDaddy.storage.updatePreference()` independently, creating a feedback loop and a divergence risk between store state and persisted state (confirmed). Three old handlers are now dead code (confirmed). The slider displays "%" for a 0-1 fractional value (confirmed).

## High-level view

The reactive store (`src/stores/Store.js`) is a minimal pub-sub with shallow-merge semantics. Each domain store is a singleton that auto-hydrates from the IPC bridge on construction and debounce-writes back. Stores are ES modules living in the renderer process.

The service layer (`src/services/`) runs in main process CommonJS and wraps `storage.js` with an in-memory cache and debounced flush. None of these services are wired into the main process yet; they're foundation code awaiting Phase 2 integration.

The shared UI components (`src/components/ui/`) are five self-registering Lit elements. All fire composed custom events (`bubbles: true, composed: true`) that cross shadow DOM boundaries correctly.

The proof-of-concept wiring replaces three controls in the Appearance section of CustomizeView, but introduces a dual-write pattern where both the store and the raw IPC bridge are called side-by-side. This keeps backward compatibility but means state can diverge if either path fails, and every interaction writes to disk twice.

<details>
<summary>Issues (5)</summary>

1. **Dual-write divergence risk** — `_handleBgTransparencySlider`, `_handleHotkeyToastsToggle`, and `_handleThemeSelect` each call both `settingsStore.set()` (which debounce-persists via its own path) and `cheatingDaddy.storage.updatePreference()` directly. If one fails silently, the store and disk disagree. Choose one persistence path per handler.
2. **Subscription feedback loop** — `settingsStore.set()` in the handler triggers the subscription callback which re-sets the same property and calls `requestUpdate()`. Lit coalesces this so it's not a bug, but it's unnecessary work on every interaction. Guard the subscription with a value-equality check or skip self-triggered notifications.
3. **Dead handlers left behind** — `handleBackgroundTransparencyChange`, `handleHotkeyToastsChange`, and `handleThemeChange` are still defined in `CustomizeView` but no longer called from any template. Remove them.
4. **Slider unit mismatch** — The transparency `cd-slider` shows `unit="%"` but the value range is 0-1. The display reads "0.8 %" instead of "80%". Either multiply for display or change the unit string.
5. **IPC listener leak in typing-store and session-store** — IPC `.on()` handlers are registered in the constructor of the singleton and never removed. For singletons this is technically fine (they live for the app lifetime), but if the module were ever re-imported or the store reconstructed during hot-reload development, listeners would stack. A `destroy()` method that calls `removeListener` would make this safe.

## Store subscription feedback loop

Consider `_handleBgTransparencySlider`:

```js
_handleBgTransparencySlider(e) {
    this.backgroundTransparency = e.detail.value;          // (1) local property
    settingsStore.set({ backgroundTransparency: ... });    // (2) triggers notify()
    cheatingDaddy.storage.updatePreference(...);           // (3) direct IPC write
    this.updateBackgroundAppearance();
    this.requestUpdate();
}
```

Step (2) fires the subscription callback synchronously:
```js
this._storeUnsubscribe = settingsStore.subscribe(state => {
    this.backgroundTransparency = state.backgroundTransparency ?? this.backgroundTransparency;
    this.requestUpdate();  // redundant re-render
});
```

Future developers adding logic inside the subscription (assuming it only fires on "external" changes) will hit unexpected behavior. A guard (`if (state.backgroundTransparency !== this.backgroundTransparency) { ... }`) would make the "external-only" intent explicit.

## Dual-write persistence and divergence

`settingsStore.set()` internally calls `cheatingDaddy.storage.updatePreference(key, value)` with a 200ms debounce. The handler *also* calls `cheatingDaddy.storage.updatePreference(...)` directly (no debounce). Every slider interaction writes to disk twice: once immediately from the handler, once 200ms later from the store's debounce. If the user moves the slider twice within 200ms, the store's debounce fires with the penultimate value, overwriting the handler's direct write.

The intended architecture is: component -> store -> persistence. The direct `cheatingDaddy.storage.updatePreference(...)` call in the handler should be removed once the store is trusted as the single persistence path.

## Unused components: cd-keybind-input and cd-setting-row

Both are registered globally via the barrel import but never used in any template in this diff. The keyboard shortcuts section in `CustomizeView` still uses raw `<input>` elements with the old `handleKeybindInput` method, meaning keybind capture logic is now duplicated: once in `CustomizeView.handleKeybindInput()` and once in `cd-keybind-input._handleKeydown()`. When the keyboard section migrates to use the component, the old handler should be removed.

## Script tag ordering and store initialization

The standalone `<script type="module" src="stores/index.js">` in `index.html` exists alongside `CheatingDaddyApp.js` already importing `sessionStore` transitively. The standalone tag's purpose is to ensure stores that *aren't* imported by any component (like `typingStore`, `uiStore`, `windowStore`) still initialize their IPC listeners at page load. If a future component imports one of these stores directly, the standalone tag becomes redundant but harmless.
